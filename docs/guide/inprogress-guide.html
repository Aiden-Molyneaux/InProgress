The ideal

Long projects with Claude lose their thread in the chat. A plan gets stated once and is then buried under a sandbox detour. The test suite Claude wrote five messages ago is still up there somewhere. Three sessions and their subagents are each working on something, and the only way to find out what is to read all of them. On a project that has run for three months, the state of play is split between the chat, the disk and your head, and the three do not agree.

InProgress keeps one tree per project in a window beside Claude. The root says what the project is for. Under it sit phases and steps, each with a status (todo, active, done, blocked or dropped) and an owner (Claude or you). A resource such as a test suite, runbook or diagram is attached to the step where it was produced, so you find it by walking the tree instead of the scrollback. Each live Claude session appears in the window with its state and the number of subagents it is running, on the step it is working on once it has claimed the step or the scribe has set its focus.

The tree is a filtered view, not a transcript. It records that the signing tests need running and, later, that they ran green. It does not record the VMware wedge you fixed on the way; that goes into the step's log as a one-line note. Steps are plan-level and have outcomes. Single actions (edit a file, run grep) never become nodes.

Claude owns the content and makes every edit to it through a background scribe, so the main session spends about one line of chat per update. The window is where you place and answer: you put steps in the order of Next, add a step to the backlog, and clear the asks that sessions raise. You also read, copy a reference like #58, and open files.

Concretely, in the kit's own example: step #58 Run signing tests is a step you do yourself, so it carries a YOU badge until you report it done. The test suite Claude wrote is resource r12 on that step. The network wedge is a log line on #55. When you ask "where are we?", the answer names those ids, and the window is already centred on them.

One local server owns the database. Everything else either reports to it or reads from it. The main Claude session never touches the tree directly: it briefs a background subagent, the scribe, whose tools come from an MCP server that only the scribe can see.

Start tracking a project

You

In a Claude session in the project folder: "track this in InProgress" (or "add this to InProgress"). Say which project if several exist, and whether to bind the folder.

Claude

The prompt hook sees the word InProgress in an untracked session and injects [InProgress] This session is not tracked yet. Session id: <id>. Use the inprogress skill to opt in. Pasted <pasted_content> blocks are stripped first, so pasting a document that mentions InProgress triggers nothing.

The skill then decides the project. If that is unclear it runs the read-only status command to list existing projects and asks you. It briefs the scribe to enrol the session, creating the project first if it is new (name, a one-paragraph purpose, an optional playbook) and binding the current folder if you agreed. For ticket work in a shared repo the binding gets a branch pattern such as *VCAD-978*, so only sessions on that branch belong to that project.

The scribe runs list_projects, then create_project (with bind_path and branch_pattern if asked), then enroll_session, and replies with the first line of the briefing.

You see

Chat: one line from Claude, in the shape ↳ InProgress: tracking this session in <project>. Window: the project appears as a tab with its root step, your session shows in the Board's header under "No claimed step" once it is working, and the activity strip walks through project created, folder bound: C:/personal/… and <session title> is working.

How a binding matches

Paths are normalised before storage and comparison: backslashes become slashes, the Git Bash form /c/x becomes C:/x, the drive letter is upper-cased, a trailing slash is dropped, and comparison ignores case. A session matches a binding when its working directory is the bound path or sits under it and, if the binding has a branch pattern, the current branch matches that glob (* any run, ? one character, case-insensitive). Among several matches the longest path wins; on equal paths, the binding with a pattern beats the one without. The branch is read from .git/HEAD by walking up from the folder (worktrees included) without spawning git. Bindings of archived projects are ignored.

Matching happens at session start. A session that already has a project keeps it; the scribe's enroll_session can repoint a session that was auto-bound to the wrong project ("this session is for X, not Y").

Background work

You

Ask for a long job: "run the full e2e suite and tell me when it's done". Claude starts it in the background and its turn ends. You go and do something else.

Claude

Three hooks follow the command. A post-tool hook, run async so it never holds a tool call, sees Bash, PowerShell and Monitor calls that came back with a background task id and posts the command's first three words (npm run test:e2e) to the server, never the command itself. InProgress's hook capture, on by default, keeps the first 80 characters of a Bash or PowerShell command in a local file under ~/.inprogress/capture/; nothing in it is posted, and credentials in the text are redacted. The Stop hook lists what is still in flight. When the command finishes, Claude Code writes a notice to the transcript, and the next prompt hook, the server's transcript watcher or a TaskStop ends the row. A subagent's commands are read from the transcript once a minute.

A message to a subagent that has finished resumes it. A SendMessage hook moves the agent to the step the message names (#168 fix round 2), or the session's current step, restarts its running time (a message within a minute of the run's start only moves it) and takes the message's summary as its description. A message sent from inside a subagent is ignored.

You see

The session's message in Now reads busy: the character breathes with its eyes open. Under its current task, a line reads ▸ a · npm run test:e2e · 4m. When the notice arrives the line shows ✓ for 5 minutes and goes, and the session goes back to idle. A command that has run 30 minutes, or is a dev, serve, preview, start or watch command, is serving: ◦ a · npm run dev · serving 3h, faint, and it does not make the session busy.

Asks, claims and scoped briefings

Asks

You

A session needs you: "which store regions at launch?", "may I force-push this branch?", "the signing change is ready to look at". You answer in chat, or in the window.

Claude

The session briefs the scribe with ask on #55: question, Which store regions at launch?. The kinds are question, permission (you must allow or do something before the session can go on) and review (finished work to look at; the step may already be done). The scribe calls raise_ask with the step, the kind, the text and the briefing session, so the answer reaches the session that asked. Raising the same open ask again joins it instead of adding a second. A session that has to stop and wait can also run inprogress ask 55 --session <id> --question "…" (or --permission, --review) itself, which raises the ask at once and prints a7 raised on #55.

When you answer in chat, the brief says a7 answered: EU and UK first and the scribe calls clear_ask. The session that raised the ask gets one line on its next prompt, Answered: a7 "EU and UK first" (yours: act on it, or add it to your tasks). If that session has ended, the step's driver gets it instead. With no answer it is Cleared: a7, no answer. Dropping a step clears its open asks; finishing a step does not.

You see

The ask sits in the Needs me column, oldest first: its kind, the text, the step, who raised it and how old it is. Answer… opens a one-line field, and sending it clears the ask with your words as the answer. Clear clears it with none. Either way the asking session hears about it as above. A session that is waiting on a tool permission shows above the stored asks as a live row; it has no buttons and goes away when the session goes on. An ask older than 7 days gets a tidy mark. The tab's count is the project's open asks plus its live permission waits.

mip-orc, the Orchestrator

You

Claude

The mip-orc skill is installed with the kit, next to the inprogress skill, in every tracked project. It never edits code, commits, builds or dispatches implementers, and it never claims a step. It changes the plan only through the scribe. It works like this:

  1. If the session is not on Opus 5.5, it says so and asks you to pick it in the model menu.
  2. It runs inprogress orchestrate --session <id> (with --status for "mip-orc status"). That makes the session the project's Orchestrator, clears its focus and prints the briefing and a counts line such as Since your last look (3d): 4 done · 2 asks raised, 1 answered · 2 sessions ended, 1 without a handoff. Marks: 3 steps. It then offers a digest, a reconcile and what's next. With --status it also prints the digest, the reconcile list and the top of Next, and shows all three at once.
  3. Digest. inprogress digest <project> [--since <iso time>] [--all]: steps done with their outcomes, asks raised and cleared with the answers, sessions started and ended (flagging those with no handoff or open tasks), steps you quick-added, your moves in Next, new documents and marks. At most 20 lines, then a +n more line; --all lifts the cap. It counts from the last look. It never repeats an ask the last digest showed.
  4. Reconcile. From the marks. A done step with no outcome, a done step a session still has focus on, or a step a session left open are mechanical fixes: the Orchestrator lists them and, after your yes, sends them to the scribe in one batch. Dropping a stale ask or closing a step are questions to you. Open tasks of ended sessions are listed, not cleared. Marking a step done ticks every task open on it at that moment, whoever left it. The task tools cannot reopen a ticked task while the step stays done, and a new task from a session still focused on a done or dropped step goes to the project root unless its subject names a step.
  5. What's next. The top of Next, each ready or not ready, and one recommended step with its reasons.
  6. Start. On your go it writes a handoff that opens with "Claim #id", attaches it to the step through the scribe (handoff on #id: "…", path …, snapshot_file, stored with purpose handoff), and offers a chip that starts the worker. The chip prompt names the model and effort to pick, because the chip cannot set them. Where the chip tool is missing, it prints the handoff path and a one-line prompt to paste. A step that is not ready needs your reason first, which it logs on the step.
  7. State note. After a full digest it writes the project's state note (state on #<root>: …, purpose state): one paragraph of where the project is, one line per top-level group, and what waits on you. The server keeps one state note per project. Adding a new one deletes the old, so the note's resource id changes each time. The note's update time is the last look for the next digest.

A session that starts with clear becomes a worker again; compaction and resume keep the role. A claim also makes the session a worker.

The live trees dist\ and web\dist\ are what the installed hooks, the scribe's MCP server and the running server execute, so nothing writes there except a deploy. Development happens beside them:

The security model

The server listens on 127.0.0.1 only and rejects any Host other than 127.0.0.1, localhost or [::1], which defeats DNS rebinding. Writes need the bearer token in ~\.inprogress\token (32 random bytes, compared in constant time) and record an actor. The page is served with a CSP that blocks inline and foreign scripts, framing and remote images. Resource Markdown is sanitised. Every write the window makes (archive, rename, delete, restore, open file, open link) must come from the window's own origin, with a JSON body, and carry a token minted per server process, so a page on another site cannot make one. Open file accepts only a stored, local, absolute file path, and launches VS Code's executable directly or Explorer's reveal, never the OS default handler and never a shell. You do not have to do anything to keep this; just do not put the token anywhere else.

To archive a project, right-click its tab (or press Shift+F10 or the Menu key on it) and choose Archive, or tell a session "archive the live-check project in InProgress" and the scribe does it through update_project. The scribe's one-line chat footprint

The main session never waits for the scribe, never sees its tools, and writes one line per update; the scribe reports in one line. That keeps the main context lean across a long session (the spec's success criterion 5). If you want more detail, the window and outline have it; do not ask the main session to narrate the tree.

The outline and status CLI

inprogress outline <project> [--full] prints the same folded text the briefing uses, with ids and resource ids; inprogress status lists projects with open-ask counts and live sessions; inprogress digest <project> lists what changed since the last look. All read without a token, so they are safe from any terminal and are how Claude reads the whole tree without the scribe.

Session titles and permission state

Session messages and the header carry the name you gave the session in the desktop sidebar, read from the transcript's newest custom-title line at each hook, so renaming a session renames it in the window at the next prompt. A session waiting on a permission prompt appears as a live row in Needs me, so you can see from the window which of three sessions needs a click.
