The ideal

Long projects with Claude lose their thread in the chat. A plan gets stated once and is then buried under a sandbox detour. The test suite Claude wrote five messages ago is still up there somewhere. Three sessions and their subagents are each working on something, and the only way to find out what is to read all of them. On a project that has run for three months, the state of play is split between the chat, the disk and your head, and the three do not agree.

InProgress keeps one tree per project in a window beside Claude. The root says what the project is for. Under it sit phases and steps, each with a status (todo, active, done, blocked or dropped) and an owner (Claude or you). A resource such as a test suite, runbook or diagram is attached to the step where it was produced, so you find it by walking the tree instead of the scrollback. Each live Claude session appears as a chip, and as a badge on the step it is working on once the scribe has set its focus, with its state and the number of subagents it is running.

The tree is a filtered view, not a transcript. It records that the signing tests need running and, later, that they ran green. It does not record the VMware wedge you fixed on the way; that goes into the step's log as a one-line note. Steps are plan-level and have outcomes. Single actions (edit a file, run grep) never become nodes.

Claude owns every edit and makes them through a background scribe, so the main session spends about one line of chat per update. The window has no edit controls: you read, navigate, copy a reference like #58, and open files.

Concretely, in the kit's own example: step #58 Run signing tests is assigned to you and carries an amber YOU tag until you report it done. The test suite Claude wrote is resource r12 on that step. The network wedge is a log line on #55. When you ask "where are we?", the answer names those ids, and the window is already centred on them.

How it fits together

One local server owns the database. Everything else either reports to it or reads from it. The main Claude session never touches the tree directly: it briefs a background subagent, the scribe, whose tools come from an MCP server that only the scribe can see.

Claude

For ticket work in a shared repo the binding gets a branch pattern such as *VCAD-978*, so only sessions on that branch belong to that project.

The scribe runs list_projects, then create_project (with bind_path and branch_pattern if asked), then enroll_session, and replies with the first line of the briefing.

You see

How a binding matches

Paths are normalised before storage and comparison: backslashes become slashes, the Git Bash form /c/x becomes C:/x, the drive letter is upper-cased, a trailing slash is dropped, and comparison ignores case. A session matches a binding when its working directory is the bound path or sits under it and, if the binding has a branch pattern, the current branch matches that glob (* any run, ? one character, case-insensitive). Among several matches the longest path wins; on equal paths, the binding with a pattern beats the one without. The branch is read from .git/HEAD by walking up from the folder (worktrees included) without spawning git. Bindings of archived projects are ignored.

Matching happens at session start. A session that already has a project keeps it; the scribe's enroll_session can repoint a session that was auto-bound to the wrong project ("this session is for X, not Y").

The stale nudge

Each typed prompt in a tracked session adds one to a counter; any write by the scribe for that session resets it to zero. Once the counter reaches two, every prompt carries one extra line into Claude's context until the next scribe write:

[InProgress] InGame · focus #57 Play app signing · 2 need you · last scribe update 3 prompts ago. If a checkpoint happened, brief the inprogress-scribe; otherwise ignore this line.

You do not see the line. You see its effect: Claude either briefs the scribe (and writes its one chat line) or carries on. If the tree looks behind to you, "where are we?" plus a sentence about what changed is enough to get it corrected. Background-task notices that arrive as prompts (the scribe finishing, a subagent hand-back) are not counted on the live build; see in flight for the remaining formats.

The outline flow and the fold rules

Order runs downward and depth indents to the right, 28 px per level, with a rail from each parent to its children. That keeps the tree narrow enough for a side window and puts the current work near the bottom. Folding keeps it short:

  • A done or dropped node with children folds into one summary row (title · n done) unless something inside it is still active, waiting on you, or focused by a session.
  • Under any parent, after the last done or active child, only the next two todo or blocked children show. Needs-you and active rows always show and do not take one of those two slots. Dropped rows show until the two slots are filled, then hide.
  • Everything past that collapses into a +n more row per contiguous hidden run, and only when at least two rows are hidden.
  • Clicking a chevron or a +n more overrides the rule for that node. Overrides are remembered per project in the browser; folding a parent again re-collapses its tail.

Follow and the keys

On load the camera centres on the frontier at zoom 1: the focus node of the most recently active working session, else the most recently updated active node, else the last row. With Follow on (the default), every event that names a node glides the camera to it, at most once per 1.5 s, and the first move waits a moment for the new row to be laid out. Dragging the canvas, scrolling the wheel, dragging or scrolling the minimap, or pressing a zoom button turns Follow off; a plain click does not. ⌖ Follow turns it back on and recentres on the frontier.

KeyDoes
NCentres the next needs-you row in outline order and flashes it; the pill does the same. A row hidden by a manual fold lands on its nearest visible ancestor.
FToggles Follow. Turning it on recentres on the frontier.
HomeCentres the project root.
EndCentres the frontier.
EscCloses the Details panel, or the resource viewer when it is open.
Tab, EnterRows, chevrons and chips are tab stops; Enter or Space on a row opens its Details, and a row focused outside the view is brought to the middle.
Shift+F10, MenuOn a tab, opens its menu (Archive, Rename… and Delete…, or Unarchive, Rename… and Delete… on an open archived project), as a right-click does.

Keys are ignored while a modifier is held or an input has focus. While the viewer is open, only Esc is handled, so Home and End scroll the document. While a tab's menu or ⋯ is open, only the menu's keys work: the arrows, Home and End move between its items, Enter or Space picks one, and Esc closes it and nothing else. Logs live in the data dir. hooks.log holds only hook failures and timeouts, one line each, and rolls over to hooks.log.1 past 1 MiB. server.log holds startup lines and errors (no per-request logging) and is truncated when it passes 5 MB at a start. The hooks never write to the chat or to stderr, so a broken install shows up as silence, which is why doctor exists.

Design rule

"Hooks never block Claude or surface errors in chat." Every hook reads stdin for at most a second, posts with a short timeout, logs on failure and exits 0. The cost is that failures are quiet; the trade was made on purpose.

Iterating on InProgress itself

The live trees dist\ and web\dist\ are what the installed hooks, the scribe's MCP server and the running server execute, so nothing writes there except a deploy. Development happens beside them:

Dev

npm run dev builds into .dev-home\dist on every change, runs a server from there on port 4318 with .dev-home as a throwaway data dir, and runs Vite on 5183 proxying /api. The installed kit keeps using the live build on 4317 throughout.

Deploy

npm run deploy runs typecheck, the vitest suite, the smoke tests against a fresh node-only build in .build\, then the Playwright tests against a full build there. Each build writes dist\build.json with the short git sha, a dirty flag and the build time. The tested trees then replace the live ones by renames, with the old ones parked in .deploy\prev\; a failed move puts everything back. claude-check compares the installed kit with what install would write now and re-runs claude-install only on a difference. npm run rollback swaps the live and previous trees and restarts. Running it again swaps back, so it also rolls forward.

The security model

The server listens on 127.0.0.1 only and rejects any Host other than 127.0.0.1, localhost or [::1], which defeats DNS rebinding. Writes need the bearer token in ~\.inprogress\token (32 random bytes, compared in constant time) and record an actor. The page is served with a CSP that blocks inline and foreign scripts, framing and remote images. Resource Markdown is sanitised. Every write the window makes (archive, rename, delete, restore, open file, open link) must come from the window's own origin, with a JSON body, and carry a token minted per server process, so a page on another site cannot make one. Open file accepts only a stored, local, absolute file path, and launches VS Code's executable directly or Explorer's reveal, never the OS default handler and never a shell. You do not have to do anything to keep this; just do not put the token anywhere else.

Archive, delete and restore

To archive a project, right-click its tab (or press Shift+F10 or the Menu key on it) and choose Archive, or tell a session "archive the live-check project in InProgress" and the scribe does it through update_project. The menu does not open the tab, and Archive asks nothing, since Unarchive undoes it; when sessions are live in the project, its second line says how many it stops tracking. Any session still running there keeps running in Claude Code, but InProgress stops tracking it: the session ends on the canvas, its own Up next entries are dropped (unowned ones stay), and nothing it does afterwards is recorded. The project's bindings stop matching and it moves into the ⋯ menu at the end of the tabs, where you can still open and read it. Unarchive it from ⋯, or through the scribe; a session that is still running there is tracked again the next time it is heard from.

Archiving the open project from its tab opens the tab to its right (to its left for the last tab), as a browser does when you close a tab. An archive by the scribe leaves the project open instead, in italic as the last tab, until you move away. An active project's tab menu has Rename… and Delete… under Archive; while an archived project is open, its tab's menu has Unarchive, Rename… and Delete…. After each of these actions a line at the bottom of the window says what happened and where the project went, for three seconds; if the server refuses, the line gives its reason and nothing moves.

Rename… turns the tab's menu into a field holding the project's name, all of it selected. Type the new name and press Enter to save it, or Escape to go back to the menu; tabbing or clicking away cancels. A name is 1 to 120 characters once trimmed, and an empty one does nothing. Only the name changes: the slug stays, so #/p/<slug> links, folder bindings and briefings keep working. The tab, the window title, ⋯ and the root step show the new name at once, the activity strip reads "you renamed the project", and the line at the bottom says "Renamed to" the new name. The scribe can rename too, through update_project.

Delete… is in every tab's menu and beside Unarchive in ⋯. It asks once, with Delete or Cancel in place of the menu, then hides the project from the tabs, list_projects, status, outline and search; a link to it opens another project. An active project is archived and deleted in one step, so its live sessions stop being tracked and their own Up next entries go, as with Archive; when sessions are live there, the confirm says how many it stops tracking. Deleting the open project opens the tab beside it, as archiving it does. For 30 days it waits under Recently deleted in ⋯ with the days it has left, and Restore brings it back as an archived project, even one that was active when you deleted it, with its name, slug and bindings (a folder you have bound to another project meanwhile stays with that project). Unarchive then puts its tab back. After 30 days the server removes it for good: its steps, logs, resources, sessions and events, and the copies of its files that InProgress keeps under ~\.inprogress\resources\ when no other project's resource names them. Files in your repos are never touched. Delete and Restore are only in the window; the scribe can archive and unarchive, nothing more. The root node still cannot be deleted on its own.
