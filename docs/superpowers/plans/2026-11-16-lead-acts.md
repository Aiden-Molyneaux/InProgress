# The lead acts (#736) Implementation Plan

> **For agentic workers:** build task by task, in order. Steps use checkbox (`- [ ]`) syntax. Sev never commits: Sigmund does.

**Goal:** The lead starts a T3 thread for a step, inside limits, and a session lands routine work itself; two per-project
switches that only Aiden turns on decide how much of that happens without his word. Both ship off.

**Architecture:** A switch is not a column: its state is the newest `allow` or `disallow` line in `lead_events` for that
switch, so no migration is needed and the log says who turned it on, with his words. `lead start` follows `lead relay`
(`src/server/lead-relay.ts`): checks, then the T3 call outside any write, then one write for the event. It uses `t3Start`
in `src/server/t3.ts`, which exists and has no caller yet. The thread starts in the project's folder with no T3 worktree:
the handoff says "Run this through Sigmund", whose phase 1 makes the session create its own worktree. The landing rule is
one line in the session briefing, printed only when the Landing switch is on.

**Tech stack:** TypeScript, better-sqlite3, vitest, React, Playwright.

**Spec:** `docs/superpowers/specs/2026-11-14-project-lead-design.md` sections 6.3, 6.4 and 6.7; the draft Aiden reads is the
resource "The lead acts: how step 3 works" on #736.

## Global constraints

- No em dashes (U+2014). Plain ASCII in everything the rules and the brief print.
- No migration, nothing under `src/server/db/`. Schema stays 20.
- Rules version becomes 5 (`LEAD_INSTRUCTIONS_VERSION = 5`); every test that pins 4 as the current version moves to 5.
- Never run the real T3 CLI in a test, and never start a real thread: tests inject the `start` function as the relay's tests inject `send`.
- Do not touch `scripts/`, `claude/`, `src/hooks/`, `src/mcp/`, `src/server/db/`.
- Ports: e2e 4410 to 4419. Never 4317 or 4399, never `~/.inprogress`.

## The bar

- C1 (Aiden, in Grok, after the gate). "start #n": a T3 thread opens, claims the step within a minute, and the brief lists it.
- C2. A start past a limit, or of a step that cannot be started, is refused with its sentence, and nothing is started.
- C3 (Aiden, after the gate). With Starts on, "where are we" ends with what he started, and why.
- C4. With Landing on, a session's briefing carries the Landing line; with it off, it does not.
- C5. `lead allow` needs Aiden's words; the brief and the Lead view show each switch, who turned it on and his words.
- C6. The Lead view lists what was started, by whom, and whether its thread has claimed the step.

## Review focus

1. A start whose T3 call times out after it may have started a thread: logged as `start_unknown`, answered 502, never retried.
2. Two starts of the same step at once: the second is refused once the first has logged, and the in-flight limit counts a started thread that has not claimed yet.
3. `allow` twice, `disallow` twice, and a switch name that is not one of the two: refused, nothing logged.
4. The daily cap counts only starts with no words of Aiden's, in the last 24 hours, in this project.
5. A project with a lead and Landing off prints no Landing line; a project with no lead prints none whatever its events say.

### Task 1: switches

**Files:** modify `src/core/lead.ts`, `src/server/lead.ts`, `src/server/lead-commands.ts`, `src/server/routes/lead.ts`, `src/server/schemas.ts`, `src/cli/lead.ts`; tests beside the existing ones.

**Produces:**

```ts
// src/core/lead.ts
export const LEAD_SWITCHES = ['starts', 'landing'] as const;
export type LeadSwitch = (typeof LEAD_SWITCHES)[number];
export const LEAD_STARTS_PER_DAY = 3;
// LeadEventKind adds: 'allow' | 'disallow' | 'start' | 'start_unknown' | 'start_failed'
export interface LeadSwitchState { on: boolean; at: string | null; words: string | null }
// src/server/lead.ts: the newest allow or disallow line per switch (text = the switch's name); on when it is an allow.
export function leadSwitches(ctx: Ctx, projectId: number): Record<LeadSwitch, LeadSwitchState>;
// src/server/lead-commands.ts
export function leadAllow(ctx, ref, as, instructions, input: { switch: LeadSwitch; aidenWords: string }): { text: string };
export function leadDisallow(ctx, ref, as, instructions, input: { switch: LeadSwitch; aidenWords?: string }): { text: string };
```

- `leadAllow`: already on: 409 `<Name> is already on.` (`Starts` or `Landing`). Else an `allow` event (`text` the switch, `aidenWords`). Reply `<Name> is on for <project name>.`
- `leadDisallow`: already off (or never on): 409 `<Name> is already off.` Else a `disallow` event. Reply `<Name> is off for <project name>.`
- Routes `POST /api/lead/:ref/allow` and `/disallow`, as the `answer` route is written; body `switch` is one of the two names (400 otherwise), `aidenWords` 1 to 2,000 characters, required for allow.
- CLI: `lead allow <project> starts|landing --aiden "<words>" --as <name> --instructions <n>`; `lead disallow <project> starts|landing [--aiden "<words>"] ...`. Usage lines.

- [ ] Tests first (state with no events, after allow, after disallow, after allow again; the refusals; another project's events do not count), then implement, then `npx vitest run test/server test/cli`.

### Task 2: lead start

**Files:** create `src/core/lead-start.ts`, `src/server/lead-start.ts`; modify `src/server/t3.ts` (`provider` and `model` become optional in `t3Start`'s `opts`; the two flags are passed only when both are set), `src/server/routes/lead.ts`, `src/server/schemas.ts`, `src/cli/lead.ts`; tests `test/core/lead-start.test.ts`, `test/server/lead-start.test.ts`, `test/server/t3.test.ts`, `test/cli/lead.test.ts`.

**Produces:**

```ts
// src/core/lead-start.ts
export interface StartHandoff { lead: string; projectName: string; stepId: number; stepTitle: string; what: string; why: string; goal: string; phase: string; onAidensWord: boolean }
export function startHandoff(h: StartHandoff): string;
export const startTitle = (stepId: number, stepTitle: string): string; // `#<id> <title>`, cut to 100 characters
// src/server/lead-start.ts
export type StartThread = (project: string, message: string, opts: { title?: string }) => Promise<{ threadId: string }>;
export const START_UNKNOWN = 'A thread may have been started. Not retried: look in T3 Code before you try again.';
export async function leadStart(ctx, ref, as, instructions, input: { stepId: number; aidenWords?: string }, start: StartThread = t3Start): Promise<{ text: string; threadId: string }>;
```

`startHandoff` returns exactly these lines (values cleaned to one line each, blank lines as shown):

```
Claim #<id> <title>. Run this through Sigmund.

Started by <lead>, the lead for <project>, <on Aiden's word | on the lead's own judgment, under his mandate>. This is not Aiden, and it is not a go-ahead to merge, deploy or push.

What: <what>
Why: <why>

Project goal: <goal>
Current phase: <phase>

First claim the step as your session briefing says, then follow the briefing.
```

`leadStart` checks, in this order, each a 409 unless said otherwise, nothing written on a refusal:

1. The step is in the project (the existing not-in-project sentence) and is not the root: `The project itself cannot be started.`
2. `#<id> is <status>.` for done or dropped; `#<id> is parked. Aiden unparks it first.` for parked; `#<id> is under parked #<n>.` under a parked ancestor.
3. A live session on the step or under it (`liveSessionUnder`): `<stepRef> already has a session working on it.`
4. A `start` or `start_unknown` event for this step in the last 10 minutes: `A thread was started for <stepRef> <n> minutes ago. Give it time to claim the step.`
5. No Goal or Phase in the intent record: `This project has no intent record yet, so nothing can be started.`
6. The step's `what` or `why` is empty: `<stepRef> has no What and Why yet. Tell Aiden.`
7. No folder (`leadFolders` is empty): `This project has no folder on record, so no thread can be started.`
8. In flight: the project's live sessions, plus `start` events of the last 10 minutes whose thread no session carries yet, at or over `IN_FLIGHT_LIMIT`: `<n> sessions are in flight, and the limit is 3. Wait for one to end.`
9. With no `aidenWords`:
   - Starts is off: `Starts is off for this project: starting a thread needs Aiden's words. Pass them with --aiden.`
   - Aiden's open asks across all projects at or over `AIDEN_OPEN_LIMIT`: `Aiden has <n> open asks, and the limit is 5. Bring those to him first.`
   - `start` events of this project with no words of Aiden's in the last 24 hours at or over `LEAD_STARTS_PER_DAY`: `You have started 3 threads on your own judgment in the last 24 hours, and the limit is 3. Ask Aiden.`

Then call `start(folder, startHandoff(...), { title: startTitle(...) })` with `folder` the first of `leadFolders`, outside any write, and log in one write as `lead-relay.ts` does for its three outcomes:

- success: a `start` event (`nodeId`, `text` the thread id, `aidenWords`). Reply: `Started a thread for <stepRef>: <threadId>. It claims the step on its first turn.`
- `T3Unavailable` that may have changed something: `start_unknown` event, 502 with `START_UNKNOWN`.
- any other failure: `start_failed` event, 502 `Not started: <the reason>`.

Route `POST /api/lead/:ref/start` (body `stepId`, optional `aidenWords`), as the relay route. CLI: `lead start <project> <step> [--aiden "<words>"] --as <name> --instructions <n>`.

- [ ] Tests first: the handoff text for both origins; each refusal with its exact sentence and no event; the three outcomes with an injected `start`; the in-flight count with an unclaimed start; the daily cap; `t3Start` without provider and model passes neither flag. Then implement, then `npx vitest run test/core test/server test/cli`.
